# D-198：Channel 选项必达、个人微信增量流与自然语言新对话设计

- 日期：2026-09-01
- 状态：用户已明确要求实施
- 前置：D-193、D-195、D-196、D-197

## 问题与根因

1. 桌面 WebSocket 打开会话后会把共享 `TurnEngine.question_asker` 替换成桌面闭包；同一引擎随后处理 Channel 入站时，桌面闭包没有记录当前 `channel_target`，因此桌面出现选项卡而企微/个人微信只停留在处理中。
2. D-196 的镜像测试只验证发送函数被调用，没有验证真实 `SendResult`；短暂发送失败也会让 Agent 永久等待而消息端无提示。
3. 官方个人微信 iLink 没有企微 `reply_stream` 的单消息原位刷新合同；现有实现只在终态发送整段正文。
4. `/new`/`/reset` 可用但发现性不足；用户自然说“开新的对话”时仍会进入模型，甚至可能被待答项当作答案。

## 设计

### 统一 ask_user 入口

- `SessionManager.inbox_question_asker` 同时接受可选桌面可见性与 inline notifier；桌面 WebSocket 不再维护第二份问题建模逻辑。
- 创建 Inbox item 时始终读取当前 Channel ContextVar。若本轮来自 Channel，则同一 item 同时：
  - 绑定精确 `platform/account/conversation`；
  - 立即镜像完整问题与选项到发起会话；
  - 桌面当前可见时继续显示同一交互卡片，任一端回答均释放同一 waiter。
- 镜像发送检查 `SendResult.ok`，在 item 仍 pending 时做有限重试；失败写运行日志，但不自动放行或猜测答案。

### 个人微信增量流

- iLink 不宣称支持单气泡原位编辑；ChemClaw 提供平台安全的“分段增量流”：
  - 开始执行先发送一次处理提示；
  - 长回答按标点/换行与长度阈值节流分段，按生成顺序发送；
  - 终态仅发送尚未送达的尾段，避免整篇重复；若流式前缀与终态不一致则发送完整终态保证正确性；
  - 每段继续使用该入站会话持久化的 `context_token`，并校验 Channel 映射所有权。
- 能力状态标记 `streaming=true`，诊断详情明确 `streaming_mode=incremental_messages`，与企微原位 stream 区分。

### 自然语言新对话

- 在去除平台 @ 标记后只做整句精确匹配；支持“开新的对话”“新的对话”“开始新对话”“新建对话”等有限同义句，以及 `/新的对话`。
- 可忽略句末常见中英文标点，但包含其它请求的长句不触发，避免误清上下文。
- 自然语言重置与 `/new` 完全复用同一原子切换、旧轮次抑制、订阅群保护和确认文案。
- 该判定优先于 `ask_user` 回答解析。

## 验收

- 桌面已打开且显示 ask_user 卡片时，企微和个人微信仍收到完整编号选项；任一端回答后同一轮继续。
- Channel 发送第一次失败、第二次成功时问题仍可达；持续失败不得被记录为已发送。
- 个人微信长回答出现有序增量段且终态不重复；短回答仍只发一次；重置后旧增量不得串回。
- 四平台私聊和自动管理群的自然语言重置与 `/new` 一致；“开新的对话然后查甲醇”不误触。
- D-196/D-197、D-193、D-195 定向回归通过；真机结果单独记录。

## 不在本任务

- 不把 iLink 描述成支持企微式单气泡原位刷新。
- 不允许 Channel 回答安全审批。
- 不构建安装程序，不合并 `main`。
